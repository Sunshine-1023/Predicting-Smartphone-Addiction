# Predicting Smartphone Addiction 数据处理流程

## 1. 这套处理要解决什么问题

这份方案只有一个版本，目标是把原始表格整理成适合 CatBoost 和 LightGBM 使用的数据，同时尽量保留可能影响比赛分数的信息。

处理时遵守四条原则：

1. 原始 CSV 永远保留，不在原文件上修改。
2. 不因为某一项缺失就删除整行数据。
3. 训练集和测试集使用同一套处理规则。
4. 不读取 `addicted_label` 来生成特征，避免把答案提前泄露给模型。

## 2. 原始数据是什么样的

训练集有 691,369 行、14 列，测试集有 296,302 行、13 列。两者的区别是：训练集多了一列答案 `addicted_label`。

每一行代表一个人，原始字段可以分成四组：

| 类型 | 字段 | 通俗解释 |
| --- | --- | --- |
| 编号 | `id` | 每行数据的唯一编号 |
| 基本信息 | `age`、`gender` | 年龄和性别 |
| 手机使用 | `daily_screen_time_hours`、`social_media_hours`、`gaming_hours`、`notifications_per_day`、`app_opens_per_day`、`weekend_screen_time` | 每天或周末使用手机的情况 |
| 生活与学习 | `work_study_hours`、`sleep_hours`、`stress_level`、`academic_work_impact` | 工作学习、睡眠、压力和受到的影响 |
| 训练答案 | `addicted_label` | 是否成瘾，只存在于训练集 |

输入特征共有 12 个，其中 9 个是数值字段，3 个是类别字段：

- 类别字段：`gender`、`stress_level`、`academic_work_impact`
- 其余 9 个字段都是数值字段

这份数据有不少空值。空值本身可能带有信息，所以不能简单地把有空值的行删掉。

## 3. 最终处理流程

### 第一步：读取并检查原始数据

先读取 `train.csv` 和 `test.csv`，然后做最基本的检查：

- 训练集必须包含 `id`、12 个输入特征和 `addicted_label`。
- 测试集必须包含 `id` 和相同的 12 个输入特征。
- `id` 不能重复。
- `addicted_label` 只能是 0 或 1，并且不能缺失。
- 训练集与测试集的输入字段名称和顺序必须一致。

如果检查失败，直接停止处理。这样可以防止列名写错、文件拿错或者数据被意外改坏。

### 第二步：把编号、输入和答案分开

- `id` 单独保存，最后生成提交文件时再放回去，默认不喂给模型。
- 12 个原始特征作为模型输入。
- `addicted_label` 单独保存为训练答案。

`id` 通常只是流水号。模型如果记住了编号规律，本地成绩可能会看起来更好，但在真正的隐藏测试集上未必可靠，所以默认不用它训练。

### 第三步：处理缺失值

#### 数值字段

数值字段的空值继续保留为 `NaN`，不统一填成平均数、中位数或 0。

原因很简单：一个人的屏幕时间没有填写，不代表他的屏幕时间等于 0，也不一定等于所有人的平均值。CatBoost 和 LightGBM 可以直接处理数值空值，强行填补反而可能制造错误信息。

#### 类别字段

下面三个类别字段如果为空，统一改成字符串 `__MISSING__`：

- `gender`
- `stress_level`
- `academic_work_impact`

这样模型会把“没有填写”当成一个独立类别。例如，压力等级为空和压力等级为 `Low` 是两种不同情况。

#### 补充缺失信息特征

除了保留空值，还要额外告诉模型“哪里缺了”。新增以下特征：

- `missing_count`：这一行的 12 个原始特征一共缺了几项。
- `missing_ratio`：缺失数量除以 12。
- `missing_pattern`：记录这一行具体缺了哪些字段。
- 每个原始字段增加一个 `_is_missing` 标记，缺失为 1，不缺失为 0。

例如，一个人的 `daily_screen_time_hours` 和 `sleep_hours` 都为空：

- `missing_count = 2`
- `missing_ratio = 2 / 12`
- 这两个字段对应的 `_is_missing = 1`
- `missing_pattern` 会记录这两个字段缺失的组合

有时“没填哪一项”比随便补进去的数值更有用。

### 第四步：增加行为组合特征

单个字段只能描述一种行为，把有直接关系的字段组合起来，模型更容易看出一个人的使用习惯。

新增四个特征：

```text
entertainment_hours
    = social_media_hours + gaming_hours

work_minus_entertainment
    = work_study_hours - entertainment_hours

known_usage_hours
    = social_media_hours + gaming_hours + work_study_hours

unaccounted_screen_time
    = daily_screen_time_hours - known_usage_hours
```

它们分别表示：

- `entertainment_hours`：社交媒体和游戏合计时间。
- `work_minus_entertainment`：工作学习时间与娱乐时间的差，反映学习和娱乐的相对占用。
- `known_usage_hours`：数据里已经明确记录用途的时间总和。
- `unaccounted_screen_time`：总屏幕时间减去已知用途时间，反映没有被这些项目解释的使用时间。

计算某个组合时，只要必要的原始字段有一个缺失，结果就保留为 `NaN`，不把缺失项当成 0。`work_minus_entertainment` 与 `unaccounted_screen_time` 即使出现负数也先保留：前者表示娱乐多于工作学习，后者可能反映不同活动时间有重叠，或者数据本身存在特殊规律。

### 第五步：增加比例和差值特征

绝对数值相同，不代表使用习惯相同。例如，同样每天看手机 8 小时，睡 4 小时和睡 8 小时的人，状态可能不一样。因此新增下面这些比例和差值：

| 新特征 | 计算方法 | 表达的意思 |
| --- | --- | --- |
| `screen_to_sleep_ratio` | 每日屏幕时间 ÷ 睡眠时间 | 看手机时间相对睡眠时间有多高 |
| `entertainment_to_screen_ratio` | 娱乐时间 ÷ 每日屏幕时间 | 屏幕时间中有多少用于社交和游戏 |
| `work_to_screen_ratio` | 工作学习时间 ÷ 每日屏幕时间 | 工作学习时间与屏幕时间的关系 |
| `weekend_minus_daily` | 周末屏幕时间 − 日常屏幕时间 | 周末比平时多用或少用多久 |
| `weekend_to_daily_ratio` | 周末屏幕时间 ÷ 日常屏幕时间 | 周末使用量相对平时放大了多少 |
| `notifications_per_screen_hour` | 每日通知数 ÷ 每日屏幕时间 | 每小时屏幕时间对应多少通知 |
| `opens_per_screen_hour` | 每日打开应用次数 ÷ 每日屏幕时间 | 每小时大约打开多少次应用 |
| `opens_per_notification` | 每日打开应用次数 ÷ 每日通知数 | 收到通知后打开应用的相对频率 |
| `notifications_minus_opens` | 每日通知数 − 每日打开应用次数 | 通知数和打开次数之间的差距 |

计算比例时，如果分母是 0 或者参与计算的字段缺失，结果保留为 `NaN`。不能生成无穷大，也不人为加一个很小的数来凑结果。

### 第六步：压缩通知数和应用打开次数

新增：

```text
log_notifications = log(1 + notifications_per_day)
log_app_opens     = log(1 + app_opens_per_day)
```

少数人的通知数或打开次数可能特别高，会把数值范围拉得很长。取对数后，大数之间的差距会变得温和一些，但原来的大小顺序仍然保留。

举个简单的例子，10 和 20 相差 10，200 和 210 也相差 10，但它们在行为上的意义未必相同。对数特征可以让模型同时看到原始次数和较平缓的变化。

原始的 `notifications_per_day` 和 `app_opens_per_day` 不删除。模型会同时拿到原值和对数值。

### 第七步：增加类别组合

新增三个类别组合：

```text
gender_x_stress = gender + stress_level
gender_x_impact = gender + academic_work_impact
stress_x_impact = stress_level + academic_work_impact
```

例如，单独看 `stress_level = High` 只知道压力高；组合以后，模型还能区分“高压力且学习工作受到影响”和“高压力但没有受到明显影响”。

类别字段在组合前已经把空值改成了 `__MISSING__`，所以组合结果不会因为其中一项缺失而丢失。

### 第八步：保证训练集和测试集完全一致

所有处理必须写成同一套固定转换，先对训练集运行，再原样对测试集运行。不能根据测试集单独发明规则，也不能让两边出现不同的特征列。

处理完成后检查：

- 训练集和测试集的特征名称、顺序、数据类型完全一致。
- 行数和 `id` 顺序没有变化。
- 新特征中不存在正无穷或负无穷。
- 三个原始类别字段不再有真正的空值。
- 原始 CSV 没有被覆盖。

## 4. 处理后的文件

最终生成三个文件：

```text
processed/train_features.parquet
processed/test_features.parquet
processed/feature_manifest.json
```

- `train_features.parquet`：训练特征、`id` 和 `addicted_label`。
- `test_features.parquet`：测试特征和 `id`。
- `feature_manifest.json`：记录原始字段、新增字段、类别字段、数值字段、处理规则和版本信息。

选择 Parquet 是因为这批数据接近一百万行。它通常比 CSV 读取更快，也能更稳定地保存字段类型。`feature_manifest.json` 相当于一张清单，方便以后确认某次训练到底用了哪些特征。

## 5. 明确不做的处理

这套方案不做以下操作：

- 不使用 `dropna` 删除有空值的行。数据量会减少，而且缺失本身可能有用。
- 不把所有数值空值统一填成平均数、中位数或 0。这样容易制造不存在的数值。
- 不对树模型做标准化。CatBoost 和 LightGBM 不需要把所有数值缩放到同一范围。
- 不使用 SMOTE、过采样或欠采样。比赛按 ROC-AUC 评价，当前类别比例不需要用这些方法强行改造。
- 不使用全局目标编码。它很容易把训练答案泄露进特征，导致本地分数虚高。
- 不生成大量没有明确含义的多项式特征。特征越多不一定越好，噪声太多还可能让验证结果变差。
- 不覆盖原始文件，也不同时维护多个处理版本。

## 6. 处理完成后怎么用于模型

处理后的数据直接进入 CatBoost 和 LightGBM。训练时使用 5 折分层交叉验证，每一折都保持 0、1 类别比例接近原始数据。

最终以各折的 OOF ROC-AUC 判断特征是否真的有效，再融合 CatBoost 和 LightGBM 输出的概率。提交文件仍然只有两列：

```text
id,addicted_label
```

其中 `addicted_label` 必须是模型预测的成瘾概率，而不是直接写成 0 或 1。

## 7. 一句话流程图

```text
原始 CSV
  → 检查列名、行数、编号和答案
  → 分离 id、输入特征和 addicted_label
  → 保留数值 NaN，填充类别空值
  → 增加缺失信息、行为组合、比例、对数和类别组合
  → 检查训练集与测试集完全一致
  → 保存 Parquet 和特征清单
  → 交给 CatBoost、LightGBM 做 5 折验证和概率融合
```

这就是本项目的数据处理定稿。后续只有在 5 折 OOF 结果明确证明某项处理更好时，才调整特征；不能根据一次 Kaggle 公榜分数随意改规则。
